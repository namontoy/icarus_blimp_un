## Skipped, by choice

**A brake, then a zero command, ends in coasting** (F1's reset of the last-written value after
a static write). The team stops the motors by coasting only, to avoid the current spike of
braking a spinning motor, and nothing in normal use brakes: STOP, Zero all, pad B, the link
timeout, the motor failsafe and every zero command coast. A brake comes only from the console's
`motor -b` or `blimp_link.py stop --brake`. Had F1 got it wrong, a brake would stay on until the
next non-zero command or STOP, motors held and undriven. Note for whoever does run it: the check
has to be made while the zero stream is still going (`blimp_link.py motor 0 0 0 0 --seconds 15`,
shafts turned by hand during it), because `blimp_link.py motor` ends with a coasting STOP that
would release a brake either way.

## Notes

- Windows kept rejoining the laptop's usual network with Internet access; the blimp's network
  had to be joined by hand, again after the power cycle. On a bench laptop, untick "Connect
  automatically" on the other network, or join with `netsh wlan connect name=<profile>` or the
  ground station's Join button.
- `blimp_link.py console` needs the command in quotes when it has options
  (`console "motor --failsafe 0"`); unquoted, argparse takes `--failsafe` for its own option.
